# Text2Cypher五层校验与自动修正实现说明

日期：2026-09-11

## 简历与实验对应关系

- 实验一对应项目内容2的“无Few-shot 65%提升至有Few-shot 85%”。
- 实验二对应项目内容2的“五层校验、自动修正与最多3次重试”，以及“Cypher查询成功执行率达90%”。这里的主语是经过完整Text2Cypher流程处理后的Cypher查询。
- 实验三应对应项目内容3的系统整体问答准确率88%和平均响应时间3.5秒，不再用来验证Cypher执行率。

## 当前生产实现

生产路径为：

```text
生成Cypher
  -> 五层校验
     1. syntax
     2. write_operation
     3. relationship_direction
     4. llm
     5. schema
  -> 无阻断错误：执行Cypher
  -> 有阻断错误且重试未满：LLM自动修正 -> 重新执行全部五层校验
  -> 3次修正后仍有错误：结构化失败，禁止执行Cypher
```

五层含义：

1. `syntax`：通过Neo4j `EXPLAIN`只解析和规划查询，不执行查询。
2. `write_operation`：在执行前拦截创建、删除、更新、合并以及数据库管理类写操作；字符串、注释和反引号标识符中的同名文本不作误报。
3. `relationship_direction`：依据Neo4j结构化Schema检查关系起点、类型和终点；可确定时直接规范方向，不能确定时作为阻断错误交给修正节点。
4. `llm`：只判断查询是否回答用户问题；字符串等值过滤由后端从Cypher确定性提取后检查能否映射到图数据库实体，避免依赖模型输出格式。
5. `schema`：独立检查节点标签、关系类型、节点属性和关系属性，并限制在当前问题对应的规范Schema切片内。

## 重试与安全语义

- `max_retries=3`表示初次生成后最多调用3次自动修正；因此最多进行4轮五层校验。
- 工作流入口和校验节点都拒绝大于3的配置，不再只是默认值为3。
- 关系方向的确定性修正发生在校验层内部，不消耗LLM修正次数。
- 校验达到上限仍失败时进入`finalize_failure`；生产配置不允许带错误查询在最后一次强制执行。
- 写查询即使连续3次修正失败，也不会进入Neo4j执行节点。
- DeepSeek超时、欠费或JSON解析失败属于运行故障，不会再触发Cypher修正；系统立即安全失败，避免浪费最多3轮修正调用并避免无依据改写查询。

## 可审计输出

每条Cypher输出新增：

- `validation_trace`：保存每轮校验的输入/输出语句、五层各自状态与错误、轮次以及下一跳。
- `correction_history`：保存每次LLM修正的修正前语句、修正依据和修正后语句。
- `attempts`：实际五层校验轮数。
- `retries`：实际自动修正次数，范围为0至3。
- LLM层的`warnings`：记录非规范`filters`等格式问题，但不把格式噪声当成Cypher错误。
- 每轮`operational_failure`：区分模型服务故障与查询内容错误。

这些字段用于后续实验二计算各层检出率、自动修正成功率、最终执行成功率和失败原因，避免从日志或最终错误反推过程。

## 2026-09-15工程加固与冒烟证据

- 修复DeepSeek将`filters`返回为字符串或别名字段时，被Pydantic格式校验误判为Cypher失败的问题。
- 映射验证改为从实际Cypher确定性提取已知STRING属性的字面量等值条件；`IS NULL`、范围、关系模式和属性间比较不再被误当作实体值。
- LLM提示词限定为语义职责，修正提示词要求最小修改并明确Neo4j 5的空值与`round(value, precision)`语义。
- 本地回归测试25/25通过。
- 3条真实后端冒烟全部通过，详见`app/test/results/text2cypher_experiment2_engineering_smoke_20260915.md`。

这些冒烟结果只证明修复有效且真实链路可用，不构成“成功执行率90%”的正式统计证据。旧实验使用了修复前代码且发生20次API欠费失败，不能与修复后结果混合；正式实验应新建检查点并从零运行。
